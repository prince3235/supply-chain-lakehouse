# Phase 3 — Synthetic Data Generation Implementation

## 1. Overview
This report documents the implementation of the Phase 3 Synthetic Data Generation framework. A robust Python ecosystem was created to programmatically generate 10 highly relational and realistic supply-chain datasets.

## 2. Dataset Ecosystem
The generator produces the following datasets matching the exact schema requirements in `DATA_DICTIONARY.md`:
- **Master Data**: `products`, `stores`, `warehouses`, `suppliers`, `calendar`, `weather`.
- **Transactional Data**: `sales`, `inventory`, `shipments`, `returns`.

## 3. Entity Relationships
Referential integrity is strictly enforced during generation:
- `products` -> `sales`, `inventory`, `shipments`, `returns`
- `stores` -> `sales`, `inventory`, `returns`, `weather`
- `suppliers` -> `shipments` -> `inventory` (via receiving)
- `sales` -> `returns`

## 4. Generation Order
1. **Time & Environment**: Calendar and Weather generated first to establish the baseline.
2. **Master Definitions**: Products, Stores, Warehouses, Suppliers.
3. **Daily Simulation**: A day-by-day loop simulates demand, fulfills sales if inventory allows, triggers shipments if inventory falls below reorder points, receives shipments, and logs inventory snapshots.

## 5. Data-Generation Methodology
The framework avoids purely random numeric generation. Instead, it simulates supply chain mechanics:
- Initial inventory is spawned for every store-product pair.
- As sales happen, inventory drops.
- `closing_inventory = opening_inventory + received - sold`.

## 6. Demand Simulation
Demand is heavily driven by learnable ML signals:
- **Base Demand**: Different baseline probabilities per store and product category.
- **Seasonality/Weather**: Food categories sell more frequently. Weather affects local demand.
- **Holidays/Weekends**: Multipliers applied to demand when `weekend_flag` or `holiday_flag` are true.

## 7. Inventory Simulation
Inventory is treated as a finite state machine:
- Stockouts occur naturally if demand outpaces supplier lead times.
- Safety stock and Reorder Points are respected.

## 8. Shipment Simulation
- Shipments are triggered dynamically when inventory hits the reorder point.
- Delivery delay logic is probabilistically tied to the `reliability_score` of the supplier.

## 9. Return Simulation
Returns are strictly simulated as a small percentage (2%) of successful historical `sales`. Returns reference a valid `transaction_id` and never exceed the original purchased quantity.

## 10. Weather Simulation
Weather is generated per location per day, with seasonal shifts (e.g., lower temps in winter) to provide external signals for demand forecasting models.

## 11. Data-Quality Injection
A separate "dirty" branch is generated by copying the clean data and injecting controlled corruption:
- `null_rate` (1%)
- `duplicate_rate` (0.5%)
- `outlier_rate` (0.2%)
Boolean columns are excluded from null-injection to prevent schema casting failures in Pandas.

## 12. Configuration
The entire pipeline is governed by `configs/data_generation.yaml`, which dictates profiles (small, medium, large), global seeds, output paths, and corruption rates.

## 13. Reproducibility
Python's `random`, `numpy.random`, and `Faker` are all seeded at the start of generation using the configured `seed`. Rerunning with the same config consistently yields identical parquet files (validated via pytest).

## 14. Output Structure
```
data/
└── generated/
    ├── clean/
    │   ├── products/
    │   ├── sales/
    │   └── ...
    └── dirty/
        ├── products/
        ├── sales/
        └── ...
```

## 15. Validation
An internal Quality Gate runs after generation to enforce:
- Primary Key uniqueness (including composite keys like `supplier_id` + `product_id`).
- Foreign Key mappings (`sales.product_id` -> `products.product_id`).
- Temporal rules (`return_date` >= `transaction_timestamp`).
The clean dataset passes 100%, while the dirty dataset intentionally flags expected errors.

## 16. Testing
`pytest` validates logic determinism, FK validity, revenue math, return quantity limits, and shipment delivery chronologies in `tests/data/test_generation.py`.

## 17. Performance
Vectorized Pandas functions are utilized wherever possible. The day-by-day simulation loop is optimized by storing active state in Python dictionaries for fast O(1) lookups before compiling to DataFrames.

## 18. Known Limitations
- The simulated sales volume on the `large` profile may take several minutes to generate due to the day-by-day event loop logic required to enforce strict inventory mechanics.

## 19. Phase 4 Readiness
The generation framework is complete, tested, and outputs Parquet files to local storage. Phase 4 (Data Ingestion) is ready to proceed.
